# 创作工具星图 · 第九轮迭代记录（v1.8.0 → v1.9.0）

> 20 轮迭代，每轮明确目标 / 改动 / 理由 / 自检。核心需求（9 条工作流 / 顶部选择 / 点击调用 / 任务包流入执行台）与整体结构全程稳定。
> 本轮问题来自四路独立深度审查（安全深水区 9 + 桥接协议 8 + 编码导出 5 + 可访问性 10 = 32 个真实发现，含 7 项"安全"判定），
> 与前两轮的 57 条零重叠。v7 审静态代码，v8 审运行时与状态，本轮审安全深水区、协议、编码边界与真实无障碍。

## ⚠️ 必须诚实交代的安全局限（轮 1/2/6）

第七轮曾把工具桥的 CORS 白名单放行了 `null` origin 与本机来源，当时判定"挡住远程恶意站"。本轮审查指出一个**根本性边界错误**：
`null` 不是"工坊页专属标识"，而是**所有 `file://` 文档共用的 opaque origin**。把整个 null 放行等于信任用户机器上任何一个本地 HTML 文件——
攻击者诱导用户双击一个 `evil.html`，其 `Origin` 同样是 null，且 `Sec-Fetch-Site` 与合法工坊完全相同（协议层不可区分）。

本轮实现的是**组合缓解**，不是根治：
- challenge token（桥端只向 `Referer` 含 `studio.html` 的请求发 token）；
- 敏感操作要求自定义头 `X-Bridge-Token`（挡住无需 JS 的 `<form>` 自动提交）；
- ping 暴露 `service/version` 供前端核对身份（挡住任意占端口的假服务）。

**局限（如实记录）**：
1. `file://` 页面是否发送 Referer 取决于浏览器。实测确认：内置浏览器预览面板发出的 Referer 是 `http://127.0.0.1:5104/`（改写过，不含文件名），用户双击 file:// 打开时是 `file:///.../studio.html`。因此最终实现同时放行两类来源（本机 http(s) 与指向 studio.html 的 file），并拒其它 file 来源。**这是功能优先的取舍**：file:// 与恶意本地 HTML 在协议层本就不可区分，任何声称能完美区分的方案都是自欺。日志对每次 file:// 放行记警告留痕。
2. 恶意本地进程（非浏览器）可伪造 Referer 与 Host，token 机制挡不住——那已超出 CSRF 威胁模型，属于"机器上已运行恶意程序"的范畴。
3. 真正根治需要架构改动：由桥自身托管带 token 的页面（`/app?token=...`）、或改用命名管道 / IPC / Electron 通道，不再依赖 `file://`。本轮未做此架构改动，以保持核心结构稳定。

## 阶段 A · 安全性（轮 1-6）

**轮 1 · 安全性** — 桥 API 无 CSRF 防护，任意网页/本地 HTML 可静默触发 launch/install。
改动：桥端加 challenge token + Referer 校验（仅放行含 studio.html 的来源）；前端取 token 后带自定义头调用。自检：临时端口实测——无 Referer 的 challenge 返回 403、正确 Referer 通过、无 token/错 token 的 POST 被拒、正确 token 通过。[达成，局限见上]

**轮 2 · 一致性/安全** — ping 返回 `{"ok":true}` 即可伪造"已连接"绿灯，service 字段前端从不校验。
改动：ping 增加 `service/version` 字段，前端核对 `d.service==='atlas-tool-bridge' && d.version` 才判为已连接。自检：实测 ping 含 version=1.9.0。[达成]

**轮 3 · 正确性/健壮性** — localStorage 历史含 null 元素时 esc(h.time) 抛 TypeError，且初始化链断裂导致桥检测永不执行。
改动：getHist 过滤非对象元素；初始化链逐项 try/catch 隔离、detectBridge 加 .catch()。自检：注入 `[null,"x",42,{...}]` 过滤后仅剩 1 条合法记录，renderHist 无异常。[达成]

**轮 4 · 边界/一致性** — localStorage 键名泛化，同源应用可冲突互挤历史。
改动：HKEY 改 `atlas:studio:v1.9:history`，一次性迁移旧键数据。自检：新键与迁移逻辑就位。[达成]

**轮 5 · 安全性** — 页面承载"启动/安装本机程序"高权限操作却无 CSP/frame-busting，可被 iframe 点击劫持。
改动：加 CSP meta（connect-src 放行桥端口）+ `top!==self` 兜底跳转。自检：CSP 与 frame-busting 就位。[达成]

**轮 6 · 安全性** — 前端用简单 POST + query 调敏感接口，攻击门槛过低。
改动：POST 改带 `Content-Type: application/json` + `X-Bridge-Token` 自定义头；桥 OPTIONS 允许该头。自检：与轮 1 实测合并验证通过。[达成]

## 阶段 B · 正确性与健壮性（轮 7-12）

**轮 7 · 正确性** — Markdown 导出无内容转义，用户输入换行/反引号可破坏表格与代码围栏，注入假标题/假任务。
改动：加 `mdInline()` 压平换行、转义反引号/竖线/行首结构符。自检：恶意输入后假标题/假任务行数均为 0；过程中发现并修正一处反引号转义失效（替换成自身）。[达成]

**轮 8 · 安全性** — TOCTOU：registry_exe 读 HKCU 卸载项，当前用户可注册假条目指向恶意 exe，桥会执行它。
改动：HKLM 优先、HKCU 仅兜底；路径规范化校验（绝对路径、拒绝 ..、仅 .exe）。自检：10/10 桌面软件探测不受影响，HKLM 优先与路径校验就位。[达成]

**轮 9 · 完整性** — install 部分成功无状态记录，失败后无指引、重试不可预测。
改动：加 install-state.json 记录 pending/succeeded/failed/manual + 时间戳 + 详情；失败提示加"检查残留"指引。自检：状态写入/读取实测通过；顺手修正一处可读性差的单行双语句写法。[达成]

**轮 10 · 正确性** — GET 无 Cache-Control，状态可能被启发式缓存导致陈旧。
改动：_json 统一加 `Cache-Control: no-store` + Pragma。自检：响应头就位。[达成]

**轮 11 · 安全性/隐私** — /api/log 泄露 exe 绝对路径与 Windows 用户名，本机任意进程可读。
改动：w() 写日志前经 _redact() 脱敏（用户目录→`<userdir>`、exe 路径→仅文件名）。自检：用 chr(92) 精确构造路径实测——`C:\Users\john\...`→`<userdir>\...`、`C:\Program Files\...\krita.exe`→`krita.exe`。**期间两次测试误报失败是测试字符串构造问题，非代码问题**。[达成]

**轮 12 · 健壮性** — 隐藏窗口进程收不到 Ctrl+C（退出不优雅）；探活仅 2 秒超时，冷启动慢会误判并启动第二实例。
改动：加 atexit 收尾日志；PS 启动器 Test-Bridge 改 3 次重试（1 秒超时 + 800ms 间隔）。自检：PS Parser 语法 OK。[达成]

## 阶段 C · 编码与兼容性（轮 13-16）

**轮 13 · 边界/国际化** — safeName 未过滤 Windows 保留名、尾随点空格、控制字符，按 UTF-16 码元截断会切开 emoji 代理对。
改动：全面加固——保留名加前缀、去控制字符/尾随点、用 Array.from 按码点截断。自检：CON→_CON、`foo. `→foo、控制字符→下划线、49汉字+emoji 截断后 50 码点且无孤立代理。[达成]

**轮 14 · 兼容性** — 导出 .md 无 BOM，旧版 Windows 记事本按 GBK 解码中文乱码。
改动：Blob 内容前加 `\uFEFF`。自检：BOM 就位。[达成]

**轮 15 · 健壮性** — 剪贴板降级 execCommand + opacity:0 脆弱（iOS 需 readOnly），且忽略返回值就报成功。
改动：textarea 加 readOnly、setSelectionRange、判断 execCommand 布尔返回值。自检：四处逻辑就位。[达成]

**轮 16 · 一致性** — README 目录树残留"七轮"（与"8 轮 160 轮"矛盾）；使用说明 UTF-8 无 BOM。
改动：README 改"八轮"；使用说明加 BOM。自检：无"七轮"残留、BOM 就位。[达成]

## 阶段 D · 可访问性与交互（轮 17-20）

**轮 17 · 可访问性** — 全局缺 :focus-visible，键盘用户 Tab 到工作流卡片/按钮时焦点不可见（WCAG 2.4.7 AA）。
改动：补全局与关键控件（wf-card/card/tbtn/button/summary）的 focus-visible 样式。自检：6 处 focus-visible 规则。[达成]

**轮 18 · 可访问性** — 全量 innerHTML 重建丢焦点，键盘用户被迫从头 Tab。
改动：refreshToolViews 前后保存 activeElement 的 data-focuskey 并恢复；按钮补稳定标识。自检：5 处 data-focuskey + 焦点恢复逻辑就位。[达成]

**轮 19 · 可访问性** — dirtyNote 靠 display 切换静态文本，读屏基本听不到"任务包已过期"而按钮已禁用；桥状态无播报。
改动：加独立 sr-only 的 dirtyLive，用文本变化驱动 aria-live；bridgeText 加 role=status；markClean 同步清空。自检：dirtyLive 与播报逻辑就位。[达成]

**轮 20 · 可访问性/健壮性** — --dim 对比度经 WCAG 公式实算仅 3.88:1（panel 背景）不达 AA 4.5:1；无 prefers-reduced-motion；桥失败无重试提示。
改动：--dim 提亮至 #8491ad；加 reduced-motion 媒体查询；失败提示加"请点工具按钮重试"。自检：对比度 3.88→5.42:1 达标。[达成]

## 终版相对基线的整体提升

| 维度 | 基线 v1.8.0 | 终版 v1.9.0 |
|---|---|---|
| 正确性 | 桥 API 可被任意本地 HTML 触发；ping 身份可伪造；历史 null 元素崩溃；Markdown 可注入 | token+Referer 组合防护；service/version 握手；数据过滤+初始化隔离；mdInline 转义 |
| 完整性 | install 部分成功无记录；导出无 BOM 旧记事本乱码；剪贴板降级忽略返回值 | install-state 状态机；BOM；readOnly+返回值判断 |
| 可读性 | README"七轮"自相矛盾；使用说明无 BOM | 八轮/九轮数字对齐；文档 BOM 兼容 |
| 性能 | GET 无 cache 控制状态可能陈旧 | no-store 保证状态实时 |
| 边界情况 | emoji 截断切代理对；保留名/尾随点/控制字符未处理；旧浏览器无 reduced-motion | safeName 全面加固；焦点可见与减少动画；对比度达标 AA |
| 一致性 | CSP 缺失；命名空间泛化；日志泄露路径用户名 | CSP+frame-busting；命名空间+迁移；日志脱敏 |
| 安全 | null origin 信任所有本地 HTML（v7 边界错误）；HKCU 卸载项劫持；点击劫持 | 组合缓解（如实标注非根治）；HKLM 优先+路径校验；CSP+token |

**核心需求稳定性**：9 条工作流支线、顶部需求选择、工具点击调用、任务包流入执行台——20 轮全程未变，终检确认。

**本轮最值得记的三件事**：
1. **安全边界要划在正确的维度上**：v7 以为放行 null 是"本地可信"，实际 null 是所有 file:// 共用的 opaque origin——防御边界划错，比不防御更危险（给人虚假安全感）。
2. **诚实标注局限比假装完美更重要**：本轮的安全加固是缓解不是根治，如实写进记录，不夸大成果。
3. **测试失败先怀疑测试本身**：轮 11 两次"脱敏失败"其实是测试字符串构造问题，代码一直正确；轮 7 的"反引号未转义"才是真 bug——分辨二者靠的是用 chr(92) 精确构造输入。

**验证方式**：全程未运行 exe、未弹系统浏览器；逻辑用 node mock DOM；安全用临时端口实跑（token/Referer/CSRF 全场景）；脱敏用精确构造字符串；对比度用 WCAG 公式实算；脚本用 PS Parser 语法校验。

**终局现场纠错（真实浏览器验证的价值）**：收尾时用内置浏览器实测，发现两个 mock 测试永远暴露不了的问题——
① 代理页面 Referer 是 `http://127.0.0.1:5104/` 而非带 studio.html 的路径，初版 Referer 校验把合法页面也拒了（日志实证 `CHALLENGE denied`）；
② 初版 frame-busting 用 `top!==self` 一刀切跳转，会破坏同源 iframe 内的预览面板。
两处均已修正：Referer 放行本机 http(s) + 指向 studio.html 的 file；frame-busting 仅跨源嵌套才跳出（用能否读取 top.location.href 判定）。
修正后用 file:// 完整链路实测（ping→challenge→token→launch）通过，恶意 `file:///C:/evil.html` 仍被 403 拒绝。
**教训：安全加固必须做真实浏览器回归，否则"加固"会先磨掉自己的功能。**
