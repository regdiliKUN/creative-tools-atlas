## ⚠️ 诚实说明

1. **交接文档的两个"卡点"判断有误**：第十一轮把"UNETLoader 选项为空""LoadImage 拒收输入图"归为 ComfyUI 节点兼容性深水区，并据此做了几项绕路修复（改输入图文件名、ComfyUI 启动前复制、拿别的模型顶替）。真正原因只有一个：8188 端口上跑着一个旧的源码克隆版 ComfyUI，测试脚本连到了它。那几项绕路修复都不是必需的；其中"模型顶替"本身是错误的，本轮已撤销。
2. **交接文档标"已解决"的 KSampler 错位实际未解决**：schema 驱动转换器仍漏算 `control_after_generate` 控件，4 个 KSampler 参数整体后移一位（`sampler_name` 被填成 7.5）。
3. **WorkBuddy 的修复建议只对了一半**：它正确定位到 RemeshMesh 缺 3 个参数，但建议的键名 `qef` 不对（ComfyUI 报错时只打印点号后最后一段，真实键名是 `sign_mode.qef`）；而且只补参数不能解决其后的错位。
4. **一次误伤**：第一份交接说明写的是"结束所有 python.exe"，范围过宽，导致无关的 evomind 服务被结束。正确做法是只结束占用 8188 的进程；测试脚本现已能自己拦截端口占用，无需手动杀进程。
5. **未在本轮执行**：app 内"一键执行"走 `automation.py` 的图生3D 路径，代码已与跑通的测试逐字节对齐（见轮 9 自检），但尚未在 app 界面里真实点一次。门禁与验证器要在 Windows 本机运行，交接时由用户执行。

**轮 1 · 根因定位：连错 ComfyUI**

**目标**：查清 UNETLoader 选项为空、LoadImage 拒收的原因。
**改动**：无代码改动，属诊断。比对 `object_info.json` 快照（UNET `[]`、VAE 只有 `pixel_space`、LoadImage 只有 `example.png`）与两份 ComfyUI 的实际目录：源码克隆版 `AI-Engine/ComfyUI/` 的 models 为空、input 只有 `example.png`，与快照完全一致；`comfy_to3d.log` 为 0 字节，说明新启动的便携版根本没起来。
**理由**：两个症状指向同一个服务端，先找共同根因，不逐个绕路。
**自检**：第二次真实测试中，`SERVER_UNET_OPTIONS` 列出 `pixal3d_bf16` 与 `trellis_2_bf16`，预检全部通过。[达成]

**轮 2 · 测试脚本：端口占用拦截 + 服务器身份确认**

**目标**：不再静默连到错误的服务器。
**改动**：`real_to3d_test.py` 启动前探测 8188，已有服务就报 `PORT_BUSY` 并退出；就绪后确认自己启动的进程仍存活，否则报 `OUR_COMFY_EXITED`；打印 `SERVER_UNET_OPTIONS`。
**理由**：端口被占时新进程绑定失败，但旧服务照样应答，脚本会"成功"连上错误的实例。
**自检**：第二次测试（端口空闲）正常通过；`PORT_BUSY` 分支逻辑已审阅。[达成]

**轮 3 · 转换器：KSampler `control_after_generate` 错位**

**目标**：4 个 KSampler 参数与 UI 一致。
**改动**：`convert_workflow_schema.py` 中，若输入的 schema 带 `control_after_generate: true`，且下一个控件值是 `fixed/increment/decrement/randomize`，则跳过它。
**理由**：UI 在 seed 后存了一个不对应任何 API 输入的控件值，原逻辑"按序消费"把它当成了 steps。
**自检**：4 个 KSampler 的 steps / cfg / sampler / scheduler 与 UI 原值逐一吻合（例：`[56,'fixed',12,7.5,'euler','normal',1]` → steps 12、cfg 7.5、euler、normal）。[达成]

**轮 4 · 转换器：被连线覆盖的控件仍占槽位**

**目标**：连线输入不导致后续控件错位。
**改动**：UI 输入项带 `widget` 键时，即使被连线，也消费一个 `widgets_values` 槽位。
**理由**：UnwrapMesh 的 `resolution` 被连线后，原逻辑没跳过它的槽位，`weld_distance` 被填成 1（按整个网格尺寸合并顶点，会把模型焊成一团）。
**自检**：`weld_distance` 恢复为 UI 原值 0.0002，padding = 1。[达成]

**轮 5 · 转换器：ComfyUI 0.45 DynamicCombo 子参数展开**

**目标**：RemeshMesh 通过服务端校验，且参数正确。
**改动**：新增递归 `_fill()`：遇到 `COMFY_DYNAMICCOMBO_V3`，按所选项依次消费其子参数，API 键名为 `<combo>.<子参数>`（如 `sign_mode.qef`）。必填校验同步展开。
**理由**：源码（`comfy_api/latest/_io.py` 的 `finalize_prefix`）确认子参数键名带前缀；UI 把子参数值紧跟在 combo 值后面存放，不展开会既漏参数又错位（`smooth_iters` 1 而非 20，`drop_small_components` 0 而非 0.01）。
**自检**：重转后只有 RemeshMesh 一个节点变化，11 个值全部与 UI 吻合；第三次真实测试通过服务端校验并产出 GLB。[达成]

**轮 6 · 转换器：数字字符串不再被误判**

**目标**：不悄悄降低上采样精度。
**改动**：schema 为 INT/FLOAT 而 UI 值是数字字符串时，先转型再校验。
**理由**：`Trellis2UpsampleStage.target_resolution` 在 UI 里存成 `'1536'`，被判非法后回退为默认 1024。
**自检**：`target_resolution` = 1536（在 1024–2048、步长 128 的合法范围内）。[达成]

**轮 7 · 转换器：可观测性——回退默认值 + 控件数对账**

**目标**：让剩余的转换偏差主动暴露，不再一轮轮撞上。
**改动**：输出两项报告：`fallback to default`（每次因 UI 值非法而回退默认值）、`widget count mismatch`（消费的控件数 ≠ UI 存的数量）。
**理由**：轮 3–6 的问题都属于"静默偏差"，提交不报错，只是结果不对。
**自检**：回退 0 项；数量不符 3 项，均已逐一确认无害——LoadImage 的上传控件状态、SaveGLB 的 UI 专用值、Trellis2UpsampleStage 已在 0.45 中删除的旧参数 49152。[达成]

**轮 8 · 模型：按官方原名补齐，撤销顶替映射**

**目标**：用正确的模型，而不是"能提交"的模型。
**改动**：补下载 `pixal3d_bf16`（11.0 GB）、`dino_v3_L_naf_fp32`（1.2 GB）、`moge_2_vitl_normal_fp16`（0.66 GB）、`birefnet`（0.44 GB），按 HuggingFace API 给出的字节数逐一校验（`download_pixal3d_models.ps1`，断点续传，可选镜像）。引擎 `adapt_workflow_models` 只保留 MoGe 连字符旧名这一处纯命名映射。
**理由**：Pixal3D 与 TRELLIS.2 是不同模型，顶替能通过校验但结果不可信。另外，旧映射遍历的键 `clip_vision_name` 并不存在（真实参数是 `clip_name`），DINO 映射其实从未生效。选 bf16 而非 int8：文件名与工作流一致，且本机 comfy_kitchen 的 cuda 后端处于禁用状态。
**自检**：`ALL_MODELS_OK`，4 个文件字节数精确吻合。[达成]

**轮 12 · 安全校验永远不过：file:// 页面不带 Referer**

**目标**：从 exe / 双击打开的工坊也能用一键执行。
**改动**：工具桥白名单托管 7 个页面与图标（`/`、`/studio.html`、`/index.html` 等，不做任意路径映射），页面与 API 同源；`start-all.bat` 启动后自动打开 `http://127.0.0.1:7843/studio.html`；`file://` 打开时，顶栏与执行台给出可点击的"用工具桥地址打开工坊"链接，并说明本地留存按打开方式分开保存。 补：已运行的旧版桥（更新前启动）不会托管页面，`start-all.bat` 会探测 `/studio.html`，失败则 `-Stop` 后重启；全程输出写入 `start-all.log` 便于排障；ComfyUI 改用 `Start-Process` 启动，避免继承日志重定向。
**理由**：桥日志连续出现 `CHALLENGE denied (referer=-)`。Chromium 对 file:// 页面发出的请求一律不带 Referer，`_referer_ok` 里放行 file://…studio.html 的分支在真实浏览器中永远走不到——一键执行从未在用户的正常打开方式下可用。前几轮的测试走 node 或带本地 http 代理的内置浏览器，所以没暴露。安全口径不变：仍只认本机 http 来源，远程网站无法伪造本机 Referer。
**自检**：在隔离副本上实跑桥：页面 200 且与源文件逐字节一致；同源 Referer 拿到令牌；无 Referer 仍拒（403 语义）；外站 Origin 拒；路径穿越 404；伪造 Host 403。JS 语法通过。[达成；界面待用户确认]

**轮 13 · 文生图拆成两条支线：AI 直接成图 / AI 在 Krita 逐笔作画**

**目标**：兑现最初的设计——出图有两条路：AI 直接出成图；AI 操控绘画软件像人一样作画。原「角色立绘」把两种方式揉在一条支线里，用户看不出区别。
**改动**：
- 「角色立绘 · AI 直接成图」：AI 生图出主图（自动）→ 锁定一致性 → 精修交付。
- 新增「角色立绘 · AI 逐笔作画」（`paintbot`，专属提示词模板，强调色块分明、平光、浅底）：AI 生图构思参考稿（自动）→ Krita 逐笔作画（自动，新步骤类型 `krita_paint`）→ 人工接手精修（原路线 A 的"人握笔 + Krita AI Diffusion"放在这里）。
- `painter/stroke_planner.py`：参考图 → 分层笔触计划（线稿 / 底色 / 明暗 / 细节 / 收边），算法为 Hertzmann 式粗到细、笔触沿等照度线弯曲，只依赖 numpy + Pillow。
- `painter/pykrita/atlas_painter`：Krita 插件，用 libkis 的 `paintLine`（线稿，带起收笔压力）/ `paintPath`（色彩）以当前笔刷真实落笔，QTimer 分片执行（可围观），结束导出 PNG、另存分层 .kra、写完成标记。
- `painter/install_krita_plugin.py`：幂等安装插件并在 kritarc 的 [python] 段启用（首次备份，保留原换行风格）。
- 引擎 `krita_paint`：取上一步参考图 → 检查 Krita 未运行（运行中则暂停提示先关闭）→ 安装插件 → 规划笔触 → 带 `ATLAS_PAINT_JOB` 启动 Krita → 轮询进度并归档。
**理由**：用户选定第②条路为"AI 在 Krita 里逐笔画"。可行性已在本机核实：Krita 5（PyQt5、Python 3.13、kritarunner），libkis 导出了 `Node.paintLine / paintPath / setPixelData / setChildNodes`、`View.setForeGroundColor / setBrushSize / setCurrentBrushPreset` 等全部所需接口。
**自检**：规划器在跑通图生3D 的同一张图上产出 11,107 笔，离线回放与参考图形体、配色一致，眼睛、喙、爪等细节可辨；安装脚本在用户真实 kritarc 的副本上运行两次，只追加 3 行、CRLF 保留、备份与原文件逐字节相同；6 个步骤标题的类型映射正确；JS / PY 语法通过。[代码达成；Krita 内真实落笔待用户首次运行确认]

**自检**：在隔离副本上实跑桥 + 引擎：两步人工作业 暂停 → 继续 → 再暂停 → 继续 → 完成，状态逐步正确；完成后再继续被拒；无 token 被拒；缩略图 200、非图片 404、路径穿越 404、伪造 jid 404、外站来源 403；非白名单打开方式 400。JS 语法通过。[达成；界面待用户确认]

**轮 16 · 「用 Krita 打开这张图」点了没反应**

**测试中发现并修复**：
- 门禁抓到：`CKPT_DIR` 引用了 200 多行之后才定义的 `COMFY_ROOT`，导入即崩。语法检查发现不了；当时工具桥正好在等图生 3D 作业结束，才没有切换到这份代码。修复：把常量提前定义；自动更新在切换前，先用独立进程真正导入一遍新代码（不启动服务），导入失败就不切换。隔离测试验证坏代码被拒。

  1. 日志显示出变体时底模又载了一份，显存只剩 2.9GB。原因是主图工作流和变体工作流的底模节点编号不同（"1" / "3"）。先试了「换工作流时让 ComfyUI 释放模型」：ComfyUI 要在工作线程下次醒来时才释放，需等它腾出显存再提交；但释放后从 I 盘重读 7GB 底模用了两分多钟（09:17:49 → 09:19:56），反而更慢，已撤回。
  2. 改为所有工作流的底模加载节点统一叫 `ckpt`（`_share_ckpt_node`，在 `submit_prompt` 里统一处理）。但仍然重载：ComfyUI 0.45 默认「内存压力」缓存，系统可用内存低于约 6GB 时会丢掉缓存的节点结果（这台机器当时只剩 7–8GB）。启动参数加 `--cache-classic` 后，变体直接复用主图的底模，不再重载。
  3. 不重载了，但批量 4 张 1024² 时一步 92 秒——ComfyUI 估算显存不够，把部分权重留在内存里算（日志 "lowvram patches"）。改为逐张出 4 张（种子依次 +1）：单张最快 3 秒。
  4. 速度仍然忽快忽慢（同一作业里一张 3 秒、一张一步 11 秒）。新增只读诊断接口 `/api/diag`（nvidia-smi + 内存占用前十的进程），查到：没有作业时显卡占用仍是 100%、显存 23.5/24.5GB，占用者是两个 Ollama `llama-server`（其中一个占内存 12GB、CPU 时间 4 万秒）、MuMu 模拟器、MAA；系统可用内存只剩 5.5GB。这不是本项目的问题，已写进使用说明（出图前关掉这些程序）。
  - 结果：主图 33–43 秒；4 张变体约 3.5 分钟（受上述程序干扰）；4 张是同一个角色（发型、服装、法杖一致，姿势 / 构图不同）；点「选这张」后作业进入「精修与交付」并暂停等人，所选文件记为变体步骤的产物。停止作业 3 次，都记为「已停止」，ComfyUI 队列同步清空。
**自检**：隔离引擎测试——变体出 4 张、挑选、非法文件名被拒、重新出、上传白名单、说明步骤不卡、可跳过的输入步骤都正确；页面脚本 `node --check` 通过；真机见各条。

**核心经验**：
1. **多个症状先找共同根因**。两个"卡点"、四轮绕路，根因只是连错了服务器。先问"这个回答来自哪个实例"。
2. **报错信息也会撒谎**。ComfyUI 显示的是 `qef`，真实键名是 `sign_mode.qef`。修之前读源码确认键名。
3. **"能提交"不等于"对"**。KSampler 错位、模型顶替、分辨率降级都能通过校验。把"静默回退"变成显式报告（轮 7），比等结果出错再查有效得多。
4. **委托说明要写清边界**。"结束所有 python.exe"误伤了无关服务；工具应自己拦截（PORT_BUSY），而不是依赖人去做范围过大的操作。

**验证方式**：真实端到端 `REAL_TO3D_OK`；GLB 结构解析与四视角渲染；app 引擎与跑通工作流逐字节等价；转换器 0 回退 / 0 缺失；门禁全套由用户在本机运行（`运行全套门禁.bat`）。不提交 GitHub。
