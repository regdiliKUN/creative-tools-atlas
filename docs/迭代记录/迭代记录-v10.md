# 创作工具星图 · 第十轮迭代记录（v1.9.0 → v2.0.0）

> 20 轮迭代，每轮明确目标 / 改动 / 理由 / 自检。核心需求（9 条工作流支线 / 顶部选择 / 点击调用本机工具 / 任务包流入执行台）与整体结构全程稳定。
>
> **审视轴**：前九轮分别审「静态代码」「运行时与状态」「安全深水区 / 协议 / 编码 / 无障碍」。本轮换一条从未走过的轴——
> **「这份交付物作为一个产品是否自洽」**：数据表之间能否互相引用得上、代码注释的承诺是否兑现、声明与实现是否一致、修复能否被门禁挡住下不为例。
>
> **问题来源**：四路独立交叉审计（六张数据表引用 / 页面声明 vs 实际数据 / 状态机覆盖 / 桥端协议契约），
> 立了 34 个检查点，改动前 28 个 FAIL。与前九轮 89 条发现零重叠。
> 全程用「实证优先」：先写只读审计脚本与 mock DOM 行为复现，把"疑似"变成"可复现"，再动刀；每轮改完立刻跑对应断言。

## ⚠️ 必须诚实交代的三件事（审计阶段的自我纠错）

1. **测试先怀疑测试本身**（延续前几轮最贵的教训）。初版行为脚本的 F1「生成后 print 可用」报 PASS、F6「历史载入重置脏基准」报 PASS，
   其实是 mock 元素 `disabled` 初值与代码切片范围造成的**假 PASS**。改用「从 HTML 解析按钮初始 disabled 集合 + 精确定位载入代码块」的探针后，
   两条才被坐实为真缺陷。另有两处假失败：`RISK` 检查里 `"社区许可" in risk_keys` 的 bool 拼进字符串导致 TypeError、
   V16b 还在找已被重构掉的 `',{},3000)` 字面量。这些都不是产品缺陷，是验证器自己的构造错误，全部先修验证器再继续。
2. **P7「/api/status 超时」在实测里并未复现**：`all_status()` 实测 0.91s，前端超时 3000ms，当前并不超时。
   因此**没有**把它包装成"已复现故障"来凑一轮。轮 15 处理的是更深一层的**最坏路径**：
   4 个 CLI 工具各 spawn 一次 `python -c import`（每个 `timeout=8`，最坏 32s）+ 注册表遍历，
   冷启动或高负载下必然超时，而 `loadToolStatus` 的 `catch(e){}` 会静默吞掉，导致所有已装工具被误显示成"一键安装"。
   这是真实的最坏路径缺陷，但本轮如实标注为"预防性加固"而非"已复现修复"。
3. **P8 首次判定为假阴性**：探针用 `return True, "([^"]+)"` 只抓到字符串字面量前缀，
   误判「launch 不回传绝对路径」。改用源码级精确检查后确认 `"已启动 " + name + " :: " + exe` 确实拼接了完整路径，
   缺陷成立并已修（轮 14）。**假阴性和假阳性一样危险**——它会让一个真实隐私问题从清单里消失。

## 阶段 A · 领域数据正确性（轮 1-5）

**轮 1 · 正确性** — `RISK` 表的键写作 `community`，而工具条目里的 `lic` 实际值是 `社区许可`。`RISK[t.lic]` 永不命中，
于是**商用模式下 Hunyuan3D 2.0 / 2.1（明确排除欧盟/英国/韩国且有大用户条款）不触发任何警示**——风险最高的一类许可反而完全静默；
`rankTools` 的商用加权与任务包第 6 节的高风险清单也一起失效。
改动：键改为与 `lic` 字面值完全一致的 `社区许可`；顺带补齐 GPL-2.0 / LGPL-2.0 / LGPL-3.0 三类此前无提示的 copyleft 风险，并补 AGPL 的 SaaS 说明。
理由：合规提示漏报比不提示更危险，会给人"已检查过"的错觉。
自检：V1/V1b 转绿；审计脚本确认 7 个 RISK 键全部能命中真实 `lic`；商用任务包实测出现「社区许可」警示。[达成]

**轮 2 · 完整性 + 正确性** — `QUALITY` 表漏配 6 个技法类工具（IP-Adapter / FaceID、InstantID / PuLID、自训角色 LoRA、三视图控制图、抠图 / 净化、锁 Seed 做变体），
`rankTools` 用 `?? 6` 静默兜底，任务包里于是凭空写出「效果分 6/10」这种**编造的数据**，而页面主打的正是"效果优先"。
改动：补齐 6 个显式评分并注明"分值表示工艺成熟度而非独立软件质量"；把兜底从伪造分数改成显式 `未评分（数据待补）`，
让以后新增工具时缺口**可见**而不是被假数据掩盖。
理由：数据缺失不可怕，用假数据填满才可怕。
自检：V2 转绿；QUALITY 键 46→52，与 52 个工具一一对应，幽灵键 0。[达成]

**轮 3 · 正确性** — 两条支线的收尾阶段错放了 `excalidraw`（手绘白板）：角色支线「精修与交付」写的是"抠图去底、FaceDetailer 修脸"，
像素支线「导出交付」写的是"导出精灵表 / 序列帧"，却都让用户去开白板。这是 v9 那次"测试误报串台"时只查 `<h3>` 标题级、没查工具名，
因而**漏掉的真串台**。
改动：前者改 `抠图 / 净化 + Krita`，后者改 `Aseprite + OpenToonz`。
理由：支线是用户照着做的操作路径，工具错配比文案错更直接地误导操作。
自检：V3/V3b 转绿；59 处支线工具引用全部指向 GROUPS 中真实存在的条目，交付/精修阶段白板工具 0。[达成]

**轮 4 · 完整性** — 9 条工作流只有 7 套提示词：`vrm`（VRM 虚拟形象）借用 `character` 的"角色设定图"模板，
`rebuild`（重建基准图）借用 `triview` 的三视图并列模板。用户选「VRM 与虚拟形象」拿到的却是画立绘的提示词，方向就偏了。
改动：新增 `vrm`（T-pose / 中性表情 / 关节清晰 / 可绑定人体）与 `rebuild`（单对象净化输入 / 无投影 / 无水印）两套 POS + NEG 模板，
并把两条支线的 `promptKind` 指过去（用上下文精确定位，避免误改同名的其他支线）。
理由：支线数量与模板数量应当一一对应，复用模板等于让两条目标共用一套产出。
自检：V4/V4b 转绿；实测 9 条工作流 ↔ 9 种 promptKind ↔ 9 套 POS ↔ 9 套 NEG。[达成]

**轮 5 · 一致性 / 防回归** — 前四轮全是"数据表之间的引用错误"，而自检套件完全没有这类断言，下次改数据还会再犯。
改动：在 `selftest.py` 新增 `check_data_contracts()`，把 5 类契约固化为可执行断言：RISK 键有效性、QUALITY 全覆盖且无幽灵键、
支线工具引用有效且交付阶段无白板串台、promptKind↔POS/NEG 双向覆盖且模板数 ≥9、T2B↔桥端 TOOLS 双向映射。
理由：一次性修复会随时间腐坏，能重复执行的契约才是防线。
自检：V5 转绿；套件实跑 `[PASS] 数据/契约 52 工具 / 7 RISK键 / 52 QUALITY / 9 模板 / 19 桥映射 全部自洽`，结果数 25→26。[达成]

## 阶段 B · 转义与状态机覆盖（轮 6-10）

**轮 6 · 正确性 / 边界情况** — v9 轮 7 加了 `mdInline()` 却只用在 `extra` 一个字段；`proj`、`subject` 这两个同样是自由文本的输入
直接拼进 Markdown 标题、概要与提示词。实测注入 `甲|乙\n# 假标题` 会在任务包里真的生成一级标题、裸竖线与假清单。
改动：新增 `promptSafe()`（压平换行与控制字符、转义反引号以免闭合代码围栏，但**保留**提示词里合法的逗号/竖线/括号，区别于 `mdInline`）；
`buildPackage` 的标题与概要对 `proj`/`subject` 用 `mdInline`，`promptPack` 的主体与补充用 `promptSafe`。
理由：转义要按目标语境分型——Markdown 文档与提示词语义不同，一刀切会把合法标点也毁掉。
自检：V7/V7b 转绿；mock DOM 复验：假一级标题 0、假清单 0、标题裸竖线 0、代码围栏开栏数仍为 3、注入内容以转义字面量出现。[达成]

**轮 7 · 正确性** — 「打印 / 存 PDF」按钮在 HTML 里初始 `disabled`，而生成任务包时只启用了 4 个按钮，漏了 `print`；
历史载入路径却启用了 5 个。**新生成的任务包永远不能打印**，只有载入历史才行。
改动：生成后的启用集合补 `print`，与载入路径对齐。
理由：同一个产出能力在两条入口上行为不一致，属于确定性功能缺失。
自检：V6 转绿；静态解析 HTML 初始 disabled 集合与 gen 启用集合，确认 `print` 两项一致。[达成]

**轮 8 · 一致性** — 历史载入只设定了 `last`（任务包内容），没重置 `lastSig`（脏检测基准）。
载入旧包后改任一字段，页面就拿"上次生成时的签名"去比对而误报过期；`save` 的内容签名也会与载入文本错配。
改动：新增 `restoreProfile()`，载入时把表单与工作流选择一并恢复到生成时参数；
`markClean()` 支持显式传入签名（优先用该历史记录保存时的 `sig`，旧格式则用恢复后的表单重建）；让输出、执行台、脏检测、保存去重四者同源。
理由：只补 `markClean()` 而不恢复表单，等于用另一份表单的签名去标记载入的内容，是更隐蔽的错配。
自检：V8/V8b 转绿；mock 复验：proj/subject 恢复为历史值、工作流恢复为 `character`、`lastSig` 与历史 sig 相同、
恢复后 `profileSig(profile())` 与历史 sig 完全一致。[达成]

**轮 9 · 边界情况** — `esc(s)` 对 `null`/`undefined` 会渲染出字面量 `"undefined"`；
`getHist()` 只过滤非对象元素却没校验字段，缺 `text`/`name` 的损坏记录（篡改存储或旧版遗留）载入后会把 `undefined` 塞进任务包输出区。
改动：`esc` 空值归一为 `""`；`getHist` 增加必要字段类型校验（`text`/`name` 必须为字符串，`prompt` 若存在必须为字符串）。
理由：本地存储是用户可改的输入面，不是可信数据源。
自检：V9/V9b 转绿；实测 `esc(null)`/`esc(undefined)` 均返回空串、`<script>` 正确转义；
注入 6 条损坏数据（null / 数字 / 字符串 / 缺字段 / 缺 text / 合法）后仅保留 1 条合法记录。[达成]

**轮 10 · 可读性 / 一致性** — CSS 里 `@media(max-width:720px)` 定义了两次，第二条是第一条的残缺子集（漏了 `.wf-grid` 单列），
重复且易误读。
改动：合并为一条，保留全部三条规则。
自检：V10 转绿；媒体查询从 `900/720/720` 变为 `900/720`，`.form-grid` 与 `.wf-grid` 单列规则均仍在。[达成]

## 阶段 C · 桥端协议契约（轮 11-15）

**轮 11 · 正确性 / 边界情况** — `do_POST` 注释写着"消费并丢弃请求体，避免残留 body 污染下一次请求"，
实现却是 `read(min(n, 65536))`：**超过 64KB 的部分仍留在 TCP 流里**，HTTP/1.1 keep-alive 下会被当成下一个请求的方法行解析，导致协议串包。
注释承诺了，代码没兑现。
改动：超限直接返回 413 并置 `close_connection = True`；合法大小精确读满 `n` 字节，对端提前断开也关闭连接。
理由：协议层串包比单次请求失败更难排查，且注释会给维护者虚假的安全感。
自检：V13/V13b 转绿；内存 mock 精确仿真：70KB body → 413 + 关闭连接 + 零读取；2 字节 body → 完整读取且不关连接；`py_compile` 通过。[达成]

**轮 12 · 完整性** — v9 引入的 `install-state.json` 状态机只覆盖了 winget 分支：
`pip` 成功 / `pip` 失败 / `TimeoutExpired` / 普通异常四条出口都直接 `return`，状态永久停在 `pending`。
用户看到"安装中"永不结束，重启也不自愈。
改动：改为单一 `final_state` 变量 + `finally` 统一落盘，另有兜底分支保证任何未预期路径都不留 `pending`。
理由：每个出口各写一次状态正是"新增分支又忘记写"的根源，收口到一处才不会再漏。
自检：V12/V12b 转绿；**验证器同步升级**——从"数调用次数"改为真实行为仿真（mock `subprocess.run`，重定向状态文件）：
pip 成功→succeeded、pip 失败→failed、超时→failed、异常→failed、winget 成功→succeeded、winget 失败→failed、手动→manual，7 个出口全对，`pending` 残留 0。[达成]

**轮 13 · 安全性 / 一致性** — v9 的日志脱敏只认反斜杠 Windows 路径。实测 `C:/Users/john/AppData/krita.exe` 带着用户名完整写进 `/api/log`
（本机任意进程可读）；桥端 glob 与 `Path` 字符串化都会产出正斜杠路径，这是真实泄露面。
改动：`_redact` 用 `[\\/]` 兼容两种分隔符，并补纯 Unix 绝对路径兜底；随后发现输出出现 `<userdir>krita.exe` 粘连（信息没泄露但可读性变差），
同一轮改成"用户目录标记保留尾分隔符 + 绝对路径只留文件名"，最终统一为 `krita.exe`。
理由：脱敏口径要跟得上代码实际产出的路径形态；脱敏结果也仍要人能读懂。
自检：V14 转绿；5 种路径形态（反斜杠 / 正斜杠 / 带空格 Program Files / 纯 Unix / 混合）实测均只留文件名，无用户名、无盘符、无粘连。[达成]

**轮 14 · 安全性 / 一致性** — `w()` 写日志时脱敏了，但 `launch()` 成功消息 `"已启动 X :: <绝对路径>"` 原样通过 HTTP 回给前端显示在页面状态栏；
同一事件在 `/api/log` 与页面上给出两种信息密度。
改动：回显改用 `Path(exe).name`，只返回文件名。
理由：脱敏要覆盖所有出口，不能只堵日志这一条。
自检：V15/V15b 转绿；伪造 `find_exe` 指向含用户名的绝对路径，实测回显 `已启动 Krita :: krita.exe`，不含用户名 / 盘符 / 反斜杠。[达成]

**轮 15 · 性能 / 边界情况（预防性，见文首诚实说明 2）** — 状态检测要 spawn 4 个子进程（每个最多 8s）+ 遍历注册表，
最坏 32s；前端只给 3s 且静默吞错。当前实测未复现，但冷启动 / 高负载下会静默误显"未安装"。
改动：桥端加 30s TTL 状态缓存（带线程锁）、`/api/status?fresh=1` 强制重算、`install` 完成后主动失效缓存；
前端超时 3000→10000，安装后用 `fresh=1`，且拉取失败时**明确提示**而非静默。
理由：静默失败比报错更糟——用户会把"未装"当成事实去重装一遍。
自检：V16/V16b/V16c 转绿；缓存实测：首次重算 19 次 `status_of`、命中时 0 次、`force=True` 重算、失效后重算，返回条数恒为 19；`py_compile` 通过。[达成]

**本轮最值得记的三件事**：
1. **换审视轴比加大审查力度更有价值**。同一份代码，前九轮按"代码对不对"审了 89 条；第十轮改问"产品自不自洽"，
   立刻又挖出 28 个真实缺陷，且零重叠——包括商用合规漏报这种影响用户决策的严重问题。
2. **注释是一种契约，也会违约**。「避免残留 body 污染」「只留任务包正文」两句注释都写得很肯定，实现却都没做到；
   把注释当断言来审，是这一轮最有效的启发式。

状态机用 subprocess mock 做 7 出口行为仿真；版本/清单用哈希与正则双向校验；Python 用 `py_compile`，PS 脚本用 Parser 语法校验。
